# Parser: обсуждение редизайна

Статус: шаги 0-4 выполнены (2026-10-23), после каждого шага вывод всех 15
тестов побайтово совпадал с эталоном — поведение то же. Осталось: шаблонный
`parseSequence` (мелочь) и семантический анализатор, куда переезжает
проверка `return`.

## Новая структура файлов (шаги 1-2)

| Файл | Содержимое |
| --- | --- |
| `main.cpp` | только `main()`: usage + вызов `runSourceFile` |
| `runners/runner.h` / `runners/runner.cpp` | конвейер: чтение файла → лексер → парсер → ошибки или дерево; единственная точка входа `runSourceFile(const string& path)`. Папка на верхнем уровне: раннер объединяет lexer и parser, это драйвер, а не часть модуля parser |
| `runners/ast_printers/ast_printer.h` / `.cpp` | печать дерева программы (первый «pass»; рядом позже встанет семантический анализатор) |
| `parser/parser.h` | публичный интерфейс: `IParser`, `makeParser` |
| `parser/parser_impl.h` | внутренний заголовок: `class Parser`, общий для трёх `.cpp` |
| `parser/parser.cpp` | инфраструктура (токены, ошибки, `parseSequence`), программа, декларации, типы |
| `parser/parser_stmt.cpp` | операторы: тело, присваивание/вызов, `while`/`for`/`if`/`print`/`return` |
| `parser/parser_expr.cpp` | выражения: цепочка приоритетов, `parsePrimary`, литералы, accessors, вызовы |

## Принятые решения

### D1. Убрать `returnType` из парсера и AST

- Удаляется поле `RoutineDeclaration::returnType` (`parser/ast.h`).
- Удаляется разбор `: Type` после списка параметров в `parseRoutineDeclaration`,
  флаг `insideTypedRoutine` и проверка в `parseReturnStatement`.
- Мотивация: проверка «`return` допустим только в рутине с типом результата» —
  семантическая, а не синтаксическая. Парсер остаётся чисто синтаксическим.
- **На семантическом анализаторе вернуть проверку:** когда известны типы рутин,
  сообщать об ошибке, если `return` встречается в рутине без типа результата.
  Это уточнение к A3 из [DECISIONS.md](DECISIONS.md): парсер принимает
  `return Expression` синтаксически всегда, ограничивает область действия
  семантика.
- Затронутое место: `main.cpp` (печать дерева) читает `routine->returnType`
  — при применении D1 его вывод тоже правится.

### D2. Runner для примеров вынести из `main.cpp`

Отдельный файл-раннер (например, `runner.cpp` + заголовок) содержит весь цикл:
чтение файла → лексер → парсер → печать дерева / ошибок. `main.cpp` сводится
к одному вызову, поэтому перенос кода требует перенести один метод, например:

```cpp
int runSourceFile(const string& path); // единственная точка входа раннера
```

## Открытые вопросы (нерешённые)

### Q1. Архитектура парсера: один класс или иерархия классов?

Если объединить цепочку функций разбора выражений в одну (precedence climbing
с таблицей операторов), не нарушает ли это разделение ответственности?
Варианты:

- **A — один класс `Parser` с приватным методом общей инфраструктуры
  (токены, `match`/`expect`, ошибки, `parseSequence`) и методом на каждую
  конструкцию грамматики.** Объединяются только однотипные уровни выражений:
  их структуру несёт таблица приоритетов, а не шесть почти одинаковых функций.
- **B — абстрактный базовый класс с общей логикой и класс-наследник на каждый
  подпарсер** (выражения, объявления, типы, операторы).

Предварительная позиция: вариант A. У всех подпарсеров одно состояние
(токены, позиция, ошибки), и при варианте B его пришлось бы протаскивать через
общий базовый класс-прослойку. Наследники оправданы, только если подпарсеры
независимы и не делят состояние.

**Решение (2026-10-23): выбран вариант A с precedence climbing.** Один класс
`Parser` с приватной инфраструктурой и методом на каждую конструкцию
грамматики. Лесенка `parseRelation → parseSimple → parseFactor → parseSummand`
заменяется одним `parseBinary(int minPrecedence)` с таблицей приоритетов
бинарных операторов; скобки переезжают в `parsePrimary`. Разделение
ответственности сохраняется: одно правило грамматики — один метод, а
приоритеты локализованы в таблице, а не размазаны по именам функций.

Отклонённые/отложенные альтернативы:
- абстрактный базовый класс с подпарсерами-наследниками — отклонён: общее
  состояние (токены, позиция, ошибки) сделало бы базовый класс прослойкой
  без полиморфизма;
- композиция с отдельной структурой `TokenCursor` для `check`/`match`/`expect`/
  `synchronize` — отложена как опция при росте парсера или появлении второго
  потребителя (например, парсера модулей);
- разбивка одного класса на несколько `.cpp` — опция при росте файла.
